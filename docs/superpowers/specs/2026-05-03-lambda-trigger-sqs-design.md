# lambda-trigger-sqs — Design

This module wires an SQS queue to an existing Lambda function by creating an `aws_lambda_event_source_mapping` and attaching the required IAM policy to the function's execution role. It is the right choice whenever a Terraform practitioner needs Lambda to consume messages from an SQS queue in a pull-based, event-driven pattern — covering both standard and FIFO queue types. The module follows the same conventions as the `lambda-trigger-dynamodb` module: pull-based event source, role-based IAM, and consistent variable shapes for batching and filtering.

## Architecture

AWS resources created by this module:

- `aws_lambda_event_source_mapping` — polls the SQS queue and invokes the Lambda function with batches of messages
- `aws_iam_policy` — grants `sqs:ReceiveMessage`, `sqs:DeleteMessage`, and `sqs:GetQueueAttributes` scoped to the queue ARN
- `aws_iam_role_policy_attachment` — attaches the above policy to the Lambda execution role

The event source mapping is the core resource. Lambda's internal poller continuously reads messages from the queue and invokes the function with a batch. The IAM policy and its attachment are prerequisites: the event source mapping carries an explicit `depends_on` on the policy attachment to ensure the execution role has queue-read permissions before the first invocation attempt.

## Components

### aws_lambda_event_source_mapping

The event source mapping drives all runtime behavior: it identifies the source queue, the target function, and the batching strategy.

Key inputs:

| Variable | Type | Default | Purpose |
|---|---|---|---|
| `function_arn` | `string` | required | ARN of the Lambda function to invoke |
| `queue_arn` | `string` | required | ARN of the SQS queue to poll |
| `batch_size` | `number` | `10` | Maximum number of messages delivered to the function per invocation |
| `maximum_batching_window_in_seconds` | `number` | `0` | Maximum seconds Lambda waits to fill a batch before invoking; `0` means invoke as soon as messages are available |
| `report_batch_item_failures` | `bool` | `false` | When `true`, sets `function_response_types = ["ReportBatchItemFailures"]` so the function can report individual message failures rather than retrying the entire batch |
| `filter_criteria` | `list(object({ pattern = string }))` | `[]` | Optional list of JSON filter patterns; only messages matching a pattern are delivered to the function |

Key outputs:

- `event_source_mapping_id` — the ID of this resource, useful for monitoring or targeting with other automation

Design decisions:

- **`report_batch_item_failures` as a boolean, not a list.** The design exposes a simple boolean rather than the raw `function_response_types` list. `ReportBatchItemFailures` is the only valid value for SQS, so a boolean is strictly cleaner and less error-prone than asking users to spell out the string.
- **No `starting_position`.** SQS has no concept of `LATEST` vs `TRIM_HORIZON` (those are DynamoDB/Kinesis concepts). Messages are consumed as they arrive; no position is required or accepted.
- **`filter_criteria` shape mirrors `lambda-trigger-dynamodb`.** The same `list(object({ pattern = string }))` type is used across pull-based trigger modules for a consistent interface. The underlying AWS resource uses identical `filter_criteria` blocks for both SQS and DynamoDB.

### IAM policy and role attachment

The IAM side consists of two resources: `aws_iam_policy.queue_read` and `aws_iam_role_policy_attachment.queue_read`.

Key inputs:

| Variable | Type | Default | Purpose |
|---|---|---|---|
| `function_name` | `string` | required | Used to name the IAM policy (`<function_name>-sqs-queue-read`) |
| `role_name` | `string` | required | Name of the Lambda execution role to attach the policy to |
| `tags` | `map(string)` | `{}` | Tags applied to the `aws_iam_policy` resource |

The policy document is generated by a `data "aws_iam_policy_document"` block and scoped narrowly to the specific `queue_arn`, granting only the three actions Lambda needs to poll:

- `sqs:ReceiveMessage` — read messages from the queue
- `sqs:DeleteMessage` — remove successfully processed messages
- `sqs:GetQueueAttributes` — inspect queue metadata (required by the Lambda service)

Design decision: **the trigger module owns its IAM policy.** Accepting `role_name` and attaching the policy directly keeps the caller's code minimal: the user provides the role name (already available as an output of `lambda-function`) and the module handles the rest. Delegating IAM to the caller would defeat the "one-stop shop" goal — every user would need to duplicate the same three-permission policy.

## Data flow

A producer writes a message to the SQS queue. Lambda's internal poller (managed by the AWS service, not user code) continuously long-polls the queue using the execution role's credentials. When messages are available, the poller accumulates up to `batch_size` messages or waits up to `maximum_batching_window_in_seconds` seconds, whichever comes first, then invokes the function synchronously with the batch.

On a successful invocation, Lambda deletes the messages from the queue. If `report_batch_item_failures` is enabled and the function returns a `batchItemFailures` response body, only the failed message IDs are left on the queue for retry; the rest are deleted. If the function throws an unhandled error and partial batch reporting is disabled, the entire batch remains on the queue and is retried until the queue's visibility timeout expires or the redrive policy moves messages to a DLQ.

## Error handling

Variable validations enforced by this module:

- None are implemented via Terraform `validation { }` blocks in the current codebase. Correctness is enforced through required variables and type constraints (`string`, `number`, `bool`, `list(object({...}))`).

AWS-side guardrails:

- If `queue_arn` does not refer to an existing SQS queue, `aws_lambda_event_source_mapping` creation fails at apply time with an AWS API error.
- If `role_name` does not exist, `aws_iam_role_policy_attachment` fails at apply time.
- The explicit `depends_on` on the IAM attachment prevents the event source mapping from being created before the execution role has queue-read permissions, avoiding a race condition where the first poll attempt would be denied.

Known failure modes:

- **No partial batch reporting (default).** A single message that causes the function to throw an unhandled error will cause the entire batch to be retried. Enable `report_batch_item_failures = true` and implement the `batchItemFailures` response format in the function to avoid this.
- **No DLQ management.** This module does not manage dead-letter queues. Users must configure a redrive policy on the SQS queue itself to cap the number of retries.
- **No maximum concurrency cap.** Lambda can scale to 1000 concurrent invocations by default. Users who need to limit concurrency must set reserved concurrency on the Lambda function directly; this module does not expose `scaling_config.maximum_concurrency`.

## Testing

- `terraform fmt -check` — verifies consistent formatting across all `.tf` files in the module
- `terraform validate` — validates resource configuration against the AWS provider schema
- Example at `examples/sqs/main.tf` — demonstrates a complete working configuration: an `aws_sqs_queue`, a `lambda-function` module, and a `lambda-trigger-sqs` module with `batch_size = 5`, `maximum_batching_window_in_seconds = 30`, `report_batch_item_failures = true`, and a `filter_criteria` pattern filtering for `body.type = ["order"]`
